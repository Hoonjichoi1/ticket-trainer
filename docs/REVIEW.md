# REVIEW.md — Task 리뷰 · 학습 기준

> 목적: Task별 리뷰의 깊이 판단 기준을 고정해, 채팅/세션마다 "중요한 부분"의 판단 편차를 없앤다.
> 사용 주체: Hoonji(학습자) + Claude(리뷰 파트너). 새 채팅에서 Task 리뷰 시작 시 이 문서를 기준으로 진행한다.

---

## 1. 깊이 4단계 (Depth Levels)

| 레벨 | 이름 | 도달 상태 | 완료 기준 |
|------|------|-----------|-----------|
| **L3** | 재현 (Feynman) | 아무것도 안 보고 설계를 화이트보드에 그리고, 선택하지 않은 대안과 트레이드오프까지 설명 가능 | 아래 §4의 L3 완료 절차 3단계 모두 통과 |
| **L2** | 코드 | 코드를 읽고 각 단계가 왜 필요한지 따라갈 수 있음. 버그 발생 시 어디를 봐야 하는지 앎 | 코드의 각 블록 목적을 내 말로 설명 가능 |
| **L1** | 개념 | 뭘 하고 왜 필요한지 한 문장 요약 가능. 코드는 보지 않음 | "X는 Y 때문에 필요하고 Z 방식으로 한다" 한 문장 |
| **L0** | 인지 | 존재와 위치만 앎. 결과만 확인 | 없음 (동작 확인으로 충분) |

## 2. 분류 질문 (위에서부터 순서대로, 걸리는 첫 레벨로 확정)

**Q1. 이력서 불릿 또는 "프로젝트 1분 소개"에서 내가 직접 언급할 내용인가?** → **L3**
- 판단이 애매하면 이렇게 환원: "SWE 인턴 이력서에 이걸 불릿으로 쓸 것인가?" 안 쓸 거면 L3 아님.
- 배경: 인턴 면접의 프로젝트 질문은 대부분 이력서와 내 소개에서 출발한다. 면접관이 팔 수 있는 것은 내가 먼저 깃발을 꽂은 지점이다.

**Q2. 이게 바뀌면 다른 Task의 코드도 바뀌는가?** → **L2 이상**
- 계약(contract)에 해당하는 것: DB 스키마, API 요청/응답 shape, 공유 타입, 상태의 진실 소스(state ownership), 트랜잭션 경계.

**Q3. 여기서 버그가 나면 내가 원인 지점을 찾을 수 있어야 하는가?** → **L2**
- 계약은 아니지만 디버깅 책임이 나에게 있는 부분: 비즈니스 로직 분기, 에러 처리 경로, 관측 데이터 기록 지점.

**Q4. Claude가 통째로 다시 만들어도 되고, 나는 동작 결과만 확인하면 되는가?** → **L1 또는 L0**
- 설정 파일, boilerplate, 스타일링. "존재 이유는 알아야 한다" 싶으면 L1, 아니면 L0.

### 운영 규칙
- **L3는 Task당 최대 1~2개.** 후보가 3개 이상이면 "이력서 불릿에 실제로 들어갈 확률"로 줄 세워 자르고 나머지는 L2로 내린다.
- **분류 먼저, 리뷰 나중.** Task 시작 시 플랜의 구성요소를 먼저 L0~L3로 분류한 뒤(Claude에게 위임 가능), L3부터 내려가며 리뷰한다. 리뷰 도중 즉석에서 중요도를 판단하지 않는다.
- 리뷰 도중 분류가 틀렸다고 판단되면 승격/강등 가능하되, **이유를 한 줄 기록**한다 (기준 자체를 개선하는 데이터가 됨).

## 3. Task 리뷰 플로우

### Phase A — 플랜 리뷰 (구현 전)
1. **분류**: 플랜의 구성요소를 §2 기준으로 L0~L3 분류 (Claude가 초안 분류 → Hoonji 확정)
2. **Scope check**: 무엇을 만들고 무엇이 명시적으로 out of scope인가
3. **설계 결정 검토**: 주요 선택지 + 채택 이유 + **선택하지 않은 대안**의 트레이드오프
4. **Out-of-scope 재확인**: 모순 없는가 (예: 타입은 정의했는데 적용 안 함)
5. **크기 적절성**: 한 Task로 적절한 분량인가
6. **명시적 verdict**: 승인 / 우려 사항 flag (설명만 하고 끝내지 않는다)

### Phase B — 구현 후 리뷰
1. Claude Code의 완료 보고를 받고, **분류표 기준으로 L3 → L2 순서로 리뷰** (L1은 한 문장 확인, L0은 스킵)
2. L2 항목: 코드를 열어 블록별 목적 확인
3. L3 항목: §4 완료 절차 수행
4. Major/Minor 이슈 triage 후 커밋 여부 결정

## 4. L3 완료 절차 (Feynman check)

세 단계를 모두 통과해야 L3 완료로 인정:

1. **역설명**: 내가 Claude에게 설계를 처음부터 설명한다 (문서/코드 안 보고). Claude는 구멍·부정확한 부분을 지적한다.
2. **스토리 재구성**: "문제 발견 → 대안 검토 → 선택 이유"를 서사로 말할 수 있는가. (ROADMAP의 D-log가 원재료)
3. **면접관 모드 꼬리물기 3단계**: Claude가 면접관 역할로 최소 3단계 파고든다.
   - 예: "설명해보세요" → "왜 그 방식인가요?" → "그 방식의 단점/한계는요?"
   - 3단계에서 무너지면 미완료. 구멍을 메우고 재시도.

> 주의: 인턴 면접에서 깊이 있는 주제를 꺼냈다가 꼬리물기 2번째에 무너지면 역효과가 크다. 꼬리물기 통과 전에는 해당 주제를 "완료"로 치지 않는다.

## 5. Claude 리뷰 파트너 행동 규칙

- 새로운 개념은 한 번에 하나씩, "X를 해라" 전에 "X가 무엇인지" 먼저 설명
- 이해 확인 후 다음으로 진행, 큰 설명/코드 덤프 금지
- 텍스트 설명이 불명확해지면 코드로 전환
- 리뷰는 반드시 verdict(승인/flag)로 끝낸다
- L1/L0 항목을 먼저 깊게 설명하지 않는다 (분류표가 깊이를 결정)
